> - **Windows 效率沒改善**：GPUI CPU 約 egui OpenGL 的 1.5–2.3 倍、GPU 3D 2.5–5 倍；5 萬列捲動 GPUI 還是 51 FPS、卡頓 63 次。egui OpenGL 捲動也不穩（6 輪有 4 輪掉到約 12 FPS）；只有 egui wgpu 6 輪都 60 FPS、0 卡頓。
> - **0.5 秒停頓結案**：Mac 看門狗「只有主執行緒卡住」0 次，3 次都是壓測包 vmmap 暫停整個程式；高頻延遲最大 288–350→62–66 ms（egui 35–41）。

> - 「不限速」（`inactive_frame_interval: None`）在 Mac、Windows 都量不出差別，留著當預防。
> - 照 10-24 的規則：改 egui 要「效率差**而且**多視窗落後」，多視窗已追平到 2–3 ms，所以不翻盤；但 Windows CPU／捲動沒解決，也還不能正式定 GPUI。

> - **多視窗修好，Mac 勉強通過門檻**：4 視窗 p50 44.8→31.1 ms、p99 49.6→35.4 ms（egui 33.4–33.5）、最慢視窗 p99 50.1→35.8 ms（egui 35.3–35.9，平手）。**Windows 還沒重跑**，整體門檻待定。

>   - 主視窗／5 萬列／重圖表那一次，是壓測包自己的 vmmap 暫停程式約 0.5 秒，發生在量測區間外。
>   - **畫面沒有真的卡住**，p50／p99 不受影響。
> - 重圖表記憶體 GPUI 321 vs egui 131 MB 沒變；（10-25 下午更正：多出來的是 malloc 沒還給系統的空塊，不是 Metal，見 [Mac 第三次](2026-10-25-mac-2/README.md)）。
> - A3（quad 畫線）在 M4 上沒有比較快、CPU 多 6–9 點，維持預設關。

> 每項 3 輪取中位數。勝負規則：**差距 5% 以內算平手**；FPS 兩邊都到螢幕更新率上限（≥ 95%）算平手；每幀繪圖時間差不到 0.5 ms 算平手（看不出來）。

## 結論先看

1. **單一視窗時，GPUI 原本最大的弱點消失了。** 在 Linux 沒顯卡時 GPUI 報價延遲中位數 74–75 ms（10-23 優化後 32–48 ms）、重圖表約 21 FPS；在這兩台電腦上，GPUI 和 egui 的延遲**都約 31 ms（p50）／33–37 ms（p99）**，重圖表（1000 條畫線、100 層）**兩邊都 60 FPS**，三種框架都 0 掉筆。
2. **但 GPUI 比較「吃資源」，Windows 上最明顯。** 同樣畫面，Windows 上 GPUI 的 CPU 約是 egui 的 **1.7–2.3 倍**、GPU 使用率 **2.3–5 倍**、GPU 記憶體 **2.3–2.8 倍**，開啟慢約 120 ms（316 vs 192 ms）。Mac 上 GPUI 的 CPU 和 egui 的 wgpu（Metal）版差不多，但比 egui 的 OpenGL 版高很多（高頻報價 30–35% vs 6–7%；每秒 10 萬筆時 egui 也到 28%）。
3. **多視窗是 GPUI 輸最多的地方。** 開 4 個視窗時，GPUI 延遲中位數 Mac 44.8 ms／Windows 43 ms，egui 只有 17.6／21.8 ms；Windows 上 GPUI p99 64.3 ms（egui 33.7），每秒畫面掉到 57–58。原因大部分在**我們自己的程式**（第 2–4 個視窗晚一幀才更新，見下面診斷），可以修。
4. **記憶體各有輸贏。** 一般畫面 GPUI 較省（Mac 101 vs 116–121 MB）；但 Mac 上重圖表 GPUI 用到 **321–329 MB，是 egui（131–141 MB）的 2.4 倍**。
5. **Windows 上 5 萬列報價表捲動，GPUI 卡頓 70 次（egui 0 次）**，捲動 51.7 FPS（egui 60）。Mac 上 GPUI 只有 2 次。
6. **GPUI 每次高頻測試都有一次 0.3–0.47 秒的停頓**（Mac 所有高頻情境、Windows 多視窗情境），egui 沒有。原因還沒查到。

**總比分（每一項指標比一次）**：Mac GPUI vs egui（OpenGL）＝ GPUI 勝 27、egui 勝 47、平手 49；GPUI vs egui（wgpu／Metal）＝ 28／47／48。Windows GPUI vs egui（OpenGL）＝ 13／33／35。

### 對選型的影響

- **之前的建議是「產品 UI 用 GPUI，但要先過 Windows 有顯卡、Windows 輸入法兩關」。** 這次 Windows 那一關的結果是：**GPUI 能用**（60 FPS、延遲和 egui 一樣、不掉筆），**但不是免費的**：CPU／GPU 約 2 倍、多視窗明顯落後。
- 所以建議**從「GPUI」改成「GPUI 有條件」**：先做下面「可以修的」A1–A3 三項，再請 Tina 在同兩台電腦重跑。
  - 如果 4 視窗延遲 p99 回到 egui 附近（約 35 ms 內）、Windows 捲動不卡，就維持 GPUI。
  - 如果修完 Windows CPU／GPU 還是約 2 倍、多視窗還是落後，**看盤核心（K 線、報價表、多視窗）就該改用 egui**，GPUI 只用在一般元件多的畫面，或整個換 egui。
- 這次**沒有任何一項是 GPUI 做不到的**（沒有掉筆、沒有卡死、沒有畫面錯）；差在效率，而效率會直接變成客戶筆電的電量和風扇聲。

### 測試包本身的問題（我們的錯，不影響上面結論）

- **Windows 重圖表 3 輪全部失敗**：壓測包只認得舊的 3 段（跳價／十字線／平移），等 10 秒沒等到結束訊號就判失敗；但程式在 10-23 加了圖層後還會再跑拖曳／選取／改順序／正確性 4 段（共約 75 秒）。程式其實都有跑，從 log 取出的前 4 段：兩邊都約 60 FPS，每幀繪圖 GPUI 1.6–2.3 ms、egui 1.1–1.7 ms，RSS GPUI 100–115 MB、egui 78–79 MB（**沒有 CPU 數字**；而且 egui 開始時記錄的圖面大小是 750×378，GPUI 大多是 1166×505，可能是在視窗調整大小前記的，只當參考）。修好後只要重跑 `-Scenarios heavy`。
- **Mac 自動摘要的勝負標記有錯**：它只拿第一名和第二名比，兩個 egui 互相差不到 5% 時，整列就被標成平手（例如重圖表 RSS GPUI 321 MB vs egui 131 MB 被標成平手）。本頁的勝負是重新算的（`analyze.py`）。
- **Windows 沒有測 egui 的 wgpu 版**（只有 OpenGL），所以 Windows 上無法分辨「新式繪圖介面的固定成本」和「GPUI 本身的成本」。
- **Windows 點選切換**：egui 有 15–17／24 次沒點到報價列，egui 的「點選切換」數字不可信；GPUI 0 次沒點到。
- **Mac egui OpenGL 版 FPS 超過螢幕 60 Hz（62–83）**：那是程式自己數的幀數，超過螢幕更新率的部分看不到，所以照規則算平手。
