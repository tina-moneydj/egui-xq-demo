# Mac 只跑重圖表：確認記憶體修正（MallocLargeCache=0）— MacBook Air M4，2026-10-25 晚上由 Tina 執行

[← 總覽與診斷](../README.md)｜[上一次（Mac 第三次，找到原因）](../2026-10-25-mac-2/README.md)

> 同一台 Mac16,12（Apple M4、24 GB、macOS 27.0.1、內建螢幕 1470×956 點 ×2、60 Hz、插電）。10-25 21:18–21:32（台北時間），只跑重圖表（20 疊加＋8 副圖＋1000 筆畫線／100 層），每項 3 輪取中位數，0 失敗。
> 版本：GPUI `70c249c`（mac-bench，含修正 `fce703e`）、egui `b9d07c1`。log 裡 `mallocLargeCache` 欄位：GPUI＝0（修正開）、對照組＝1（`XQ_MALLOC_LARGE_CACHE=1`，恢復系統預設）。
> 完整表格：[raw/summary.md](raw/summary.md)；原始檔：[raw/](raw/)、記憶體分區表 [raw/vmmap/](raw/vmmap/)（已去掉電池序號；電腦名稱本來就是 `mac`）。

## 結論先看

1. 🏆 **修正在 Tina 的 M4 上確認有效：重圖表 RSS 321 → 115 MB（−206 MB，−64%），實體記憶體 370 → 159 MB（−212 MB）。**
2. 🏆 **GPUI 從重圖表記憶體最差，變成四版裡最省**：RSS 115–121 MB，egui wgpu 131–137 MB、egui OpenGL 134–141 MB；實體記憶體 GPUI 159 MB、egui wgpu 190、egui OpenGL 203。
3. **vmmap 證實那 201 MB 不見了**：對照組（修正關）有「Malloc Large (empty)」201 MB（128 塊、已 free 但還佔著記憶體）；GPUI（修正開）這一列整個沒有，egui 兩版也沒有。
4. **FPS 不受影響**：四版每段都 60 FPS（egui OpenGL 62–63 是程式自己數的，超過螢幕 60 Hz，算平手）。0 次「只有主執行緒卡住」的停頓。
5. **代價：CPU 多 1–6 個百分點**。修正開 vs 關：跳價 32.0 vs 31.1 %、十字線 35.6 vs 29.7 %、平移 32.6 vs 27.4 %、拖曳 30.7 vs 26.9 %；每幀繪圖多 0.1–0.4 ms。原因：記憶體每次用完就還給系統，下一幀要重新跟系統要。CI 虛擬機也看到同樣幅度（0–10 點）。
6. **CPU 仍是 egui OpenGL 最省 🏆**（重圖表 17–25 %），GPUI 和 egui wgpu 差不多（GPUI 31–36 %、wgpu 25–36 %）。這一項跟修正無關，之前就是這樣。
7. **對選型的影響**：之前「重圖表記憶體 GPUI 2.4 倍」這個缺點**消除了**。剩下沒過的是 **Windows 效率**（CPU／GPU 約 2 倍、5 萬列捲動卡頓），所以整體仍是「GPUI 有條件」。
8. 下一步（可選）：若想把多出的 CPU 拿回來，做法是重用每幀的畫線暫存（不每幀 free／malloc），這樣記憶體和 CPU 都省；目前不急。
