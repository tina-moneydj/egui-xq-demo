## 0.3–0.5 秒「停頓」：查到的原因（2026-10-25）

**結論**：有兩個來源，都不是 GPUI 畫面真的卡住。

1. **高頻／多視窗的「延遲最大」288–481 ms 是量法造成的假象**〔推論，證據強：在 Linux 完全重現，修了量法就消失〕。
   - 我們量「報價送出 → 畫到畫面上」的方式，是在報價畫進某一幀之後，等**下一幀開始**時記時間。
   - 測試結束時報價停了。最後一包畫完之後，沒有東西再叫視窗畫下一幀，所以這一包要等到程式每秒一次的取樣才補記時間。這一等就是 0.3–1 秒。
   - 所以每輪剛好一筆、而且都在最後一包。egui 沒有這個問題：egui 版的量測程式在有樣本等著時會主動排一次 16 ms 後的重畫（`request_repaint_after`），GPUI 版漏了這一步。Windows 的高頻測試會一直點報價列切換，切換會觸發重畫，所以沒有；Windows 的多視窗測試不點，就有。這和第一次看到的規律完全一樣。
   - **Linux 重現**（同一個壓測包，llvmpipe 軟體繪圖）：每秒 1 萬筆，最慢一筆在第 30.0 秒（最後 15 ms 送出），「套用 → 下一幀」307 ms，其他時間最慢 53–63 ms。4 視窗時最慢一筆同樣在第 30.0 秒，322.9 ms。
   - **修法**（`src/tickbench.rs`、`src/main.rs`）：每個視窗本來就有一個 25 ms 的後備計時器。現在它看到「有一包已經畫好、超過 25 ms 還沒等到下一幀」時，就叫一次重畫。修完後在 Linux 重跑：最後一包在結束後 50 ms 內記到；最慢一筆每秒 1 萬筆 128 ms（在剛開始的第 0.2 秒，是軟體繪圖暖機），4 視窗 159.9 ms（第 24.5 秒）；第 30 秒的那一筆不見了。
   - 這只影響量測，不影響程式平常的行為：報價一直來的時候本來每幀都在畫，多叫的那一次只發生在報價停下來之後。
2. **主視窗／5 萬列／重圖表各一次約 0.5 秒停頓，是壓測包自己的 `vmmap`**〔確定〕。
   - 壓測包用 macOS 的 `vmmap` 量「實體記憶體」，vmmap 會把被量的程式整個暫停約 0.5 秒。
   - GPUI 的長幀記錄時間點，和 vmmap 執行時間（主視窗第 10.8 秒、5 萬列第 42.3 秒、重圖表第 67.4 秒）完全對上。egui 主視窗在同一秒也掉到 16 FPS（3 輪都是），只是 egui 沒有長幀記錄。
   - vmmap 只在量測區間外執行，**表格裡的數字不受影響**。

**新版壓測包多記的東西**（萬一還有真的停頓，下一次就能抓到）：
- GPUI 程式內建停頓看門狗：主執行緒超過 120 ms 沒動，就記下「卡在哪一步、是不是整個程式被暫停」，並自動用 macOS 內建的 `sample` 抓呼叫堆疊（`stalls/` 資料夾）。
- vmmap 的起訖時間。
- 最慢那一筆在第幾秒、卡在哪一段（網路、等主執行緒、等下一幀）。
- GPUI 內部的 log。

## 重圖表記憶體：拆解（2026-10-25）

- **Mac 上什麼時候長上去**（這次的 log）：重圖表剛建好時 113.8 MB，跑「跳價」那 10 秒長到 320.8 MB，之後各段 290–326 MB。同一時間主視窗大約一直是 100 MB。
- **我們程式自己的部分很小**：畫線快取 313 條、10,758 個頂點，換算不到幾 MB。
- **Linux 不會這樣長**：同一個情境，剛建好 300.8 MB，跑完 318 MB，只多 17 MB。Linux 的 RSS 主要是：
  - GPU 驅動的共享記憶體約 141 MB
  - 程式碼和字型檔對映約 110 MB
  - heap 區約 45 MB、其他匿名記憶體約 23–26 MB
  - 另外 malloc 的帳上用量是 93–95 MB（這個數字包含還沒實際佔用的部分，所以不能跟上面幾項直接相加）
- **推論**：Mac 多出來的約 200 MB，是在 GPUI 的 Metal 繪圖層或系統配置器裡長的（例如每幀的繪圖指令緩衝池只長不縮、Retina 2 倍解析度的暫存貼圖）。不是我們的資料結構。
- **這次沒有做減法**：在 Linux 上量不到 Mac 的這種增長，改了也無法驗證有沒有效。先把記憶體拆開記：
  - 程式自己記 `heapUseMb`／`heapAllocMb`（malloc 實際在用的量和向系統要的量）。
  - 壓測包把 vmmap 的分區表（MALLOC、IOAccelerator／IOSurface＝GPU、程式碼、對映檔）存到 `vmmap/`。
  - 下一次 Mac 重跑就能知道那 200 MB 是 malloc 還是 GPU 緩衝區，再決定怎麼減（例如定期縮小 GPUI 的緩衝池，要改 GPUI 原始碼）。

## 多視窗不限速（2026-10-25 加的修補，這次的數字還沒有包含）

- GPUI 預設會把「沒有焦點的視窗」限速：只要該視窗有每幀回呼，就最多約 30 fps，60 Hz 下實際約 23 fps（`inactive_frame_interval`，見下面參考資料）。
- 現在所有視窗都設 `inactive_frame_interval: None`。另外在 macOS 啟動時申請「延遲敏感」模式，避免背景視窗被 App Nap 拖慢。
- 我們的報價更新走 `notify`，本來就不會被限速。所以這個修補主要是預防：以後加動畫、拖曳中的每幀更新時，就不會踩到限速。
- 在 Linux 4 視窗前後交錯各量 3 次，**沒有可量到的差別**：
  - 中位數 p50 184.6 vs 186.1 ms、p99 249.7 vs 269.6 ms。
  - 這台是 4K 軟體繪圖，只有約 12 fps，旁邊還有別人的 Android 模擬器在吃 CPU，雜訊比這個差大。
- 新版壓測包多一欄「GPUI 舊設定（gpui-nofix）」，在 Mac 上直接比前後。

## 參考：另一個內部 Mac 試驗的發現（數字不能直接跟本頁比，機制可以參考）

以下來自另一組 Mac 試驗（2026-10-21～22，負載是 mock 報價表＋K 線，不是本專案的壓測包）。

- **GPUI 背景視窗限速**：開 2 個以上視窗、用 `on_next_frame` 排畫時，只有有焦點的視窗 60 fps，其他每個約 22.5–23.7 fps；各視窗畫完時間差 p95 35–39 ms。設 `inactive_frame_interval: None` 後 1–8 個視窗全部 60 fps、時間差 p95 1.4–4.1 ms。只用 `cx.notify()` 排畫不受影響。
- **閒置喚醒**：閒置時 egui 0.0% CPU、每秒 0.1–0.3 次喚醒；GPUI 0.5–0.7% CPU、每秒 15–35 次喚醒，不隨視窗數增加。原因是 GPUI 的 display link：視窗看得見時每個 vsync 都叫醒主執行緒問「要不要畫」。這是框架設計，本專案層關不掉。
- **中文／emoji 顯示（豆腐字＝顯示成方框）**：
  - GPUI 桌面 0 個豆腐字：系統字型自動補字，韓文、彩色 emoji、國旗都正常。
  - egui 桌面：韓文全部是豆腐；emoji 是單色；🇹🇼 變成「TW」、1️⃣ 變成「1」。原因是 egui 只用自己載入的字型，要另外載韓文和 emoji 字型。
  - GPUI web 版：全形字（｜％ＡＢＣ１２３）和注音符號、聲調全部是豆腐，要另外載一份中文字型。
- **egui 報價表的寫法差很多**：用 `Painter` 自己畫＋快取時，指令數是 GPUI 的 0.86–1.26 倍；用 `TableBuilder` 時是 2.5–3.4 倍，CPU 30–34%，每幀配置 4,800–10,000 次（GPUI 160–450 次）。要接高頻報價就用 Painter，不要用 TableBuilder。本專案的 egui 版已經是自己畫。
- **GPUI web 版不需要 nightly**：關掉 `gpui_web` 的預設 `multithreaded` 功能，用 stable Rust 就能編過，單執行緒可以跑到 60 fps。要多執行緒才需要 nightly。
